# Build a phone agent from a brief

You are the builder. Input: one or more brief files, a tool API file (OpenAPI JSON), a slot name, and sometimes a cases file for practice. Output: `out/gen_<slot>.py` (your generator), `out/<slot>.workflow.json` (what it emits), saved on Freya under the slot. Work from the repo root.

Use ONLY what the given brief(s) and tool API file say. Never copy a rule, value, date, name, enum or sentence from another brief, from the reference generators, or from memory. Hidden briefs differ from the kit's in every dimension: identity questions, wrong-answer limits, calendars and holidays, bands and deadline formulas, floors, attempt counts and proposals, outcome/reason tables, verbatim sentences, callback windows, tool fields and enum values. Customers can have one to three products. A brief can be raw material (a mail, a policy extract, a memo that changes it, a code list): a later document overrides an earlier one; apply the rule in force.

## The brief decides the scenario (read this first)

The library and the steps below were written on collections briefs (identity check, debt, payment promise). A brief can be a different call altogether: an inbound service line, a balance or statement enquiry, a change of a setting, an e-mail confirmation. Then:

- **Take the flow from the brief** (its flow drawing, analysis document, decisions in e-mails and meeting notes), not from the collections steps. Skip every library part the brief has no use for (identity questions, `Policy`, promises, bands, floors). Keep the architecture rules: a conversation node first, facts computed in code nodes, routes on tool results / extracted enums / flags written by code, one `end_pair`-style terminal per way a call can end, every path reaches an `end_call`, no `test_variables`, hooks that write `what_to_do_next`.
- **Language.** Every spoken word (opening, prompts' example lines, verbatim sentences, tts lines, farewells, `what_to_do_next` hints the model repeats) is in the language the brief says the calls are in. The system prompt says so in one line and also says: speak only that language; a caller in another language gets the brief's prescribed line. Rule inventories and code comments may stay English. Number words, currency names, ordinal words, date formats ("21 Ağustos 2026"), digit-by-digit reading and amount reading (whole units and sub-units in words) follow the brief's examples: implement them as functions in a code node in that language and hand the model finished sentences; never leave money or dates to the TTS when the brief prescribes how they are spoken. Never route on or speak abbreviations the brief forbids.
- **Case folders** (`out/<slot>.brief.md` is a bundle of the bank's documents, each under `DOCUMENT FILE:`): the newest dated decision wins (meeting notes and later e-mails override an older analysis; a "TBD" is not a rule; a web FAQ or an IVR prompt sheet describes TODAY'S other channel, not the agent, unless a decision adopts it). Sentences the documents give verbatim are quoted exactly, with the brief's placeholders filled from service data or code. Test data (names, numbers, cards) is for your smoke tests only, never for prompts.
- **Call variables** are the ones the brief names (e.g. a customer number and `now`); bake them into tool bodies with `baked={"<api field>": "{{<variable>}}"}` when the API field has another name. The agent never asks for a value a call variable already carries.
- **A derived tool API** (`out/<slot>.openapi.json`, written by `builder/apispec.py` from the bank's integration document when the bank sent no OpenAPI file): tool names are the `operationId`s, the url is `servers[0].url` + the real path, request fields are flat (the mock accepts the fields with or without the bank's envelope). Read its `x-notes` and the integration document itself: the response envelope, how success is recognised (e.g. HTTP 200 plus a return code), which status code means "not found" vs "technical error", which calls have side effects and must not be retried, and latency warnings (set `timeout_ms` above the slowest answer the documents mention). Response mappings start with `data.` followed by the path inside the HTTP body (`data.data.cards` when the body itself has a `data` object). Lists: map what you need per item in code (`result['data']...`) and store simple strings/JSON strings in variables; the model must never invent ids, card numbers or amounts: everything it says about them comes from a tool result or a code-built sentence.
- **Mock facts for smoke tests**: the bundle's test-environment files list the customers the mock serves; use a plain one for the chat smoke (pass the call variables with `--vars`), and a multi-record / error / missing-data one when time allows. Service errors route to the brief's error ending, never silently on.

## Procedure

1. **Read everything.** The brief(s) in full, then the tool API file (every path, field, enum, description, required list), then the rule inventory `out/<slot>.rules.json` and `.md` (made before you started; if absent run `python3 builder/rules.py <briefs> --api <api> --out out/<slot>.rules.json`). Every rule `in_force` must end up implemented somewhere.
   - **Resolve `out/<slot>.rules.conflicts.md` first**: rules only one extraction sample found, values the samples disagree on, values a fresh reader could not confirm from a quote, the dated decisions (which statement is in force, with the deciding quote) and spec problems. For each item re-read the quoted source sentence in the brief and decide; the brief wins over the inventory.
   - **Use `out/<slot>.spec.json`** (schema at the top of `builder/spec_check.py`): calendar, bands with deadline rules, floors, attempt ladder, callback window, identity order, wrong-answer limit, outcomes, note reasons, verbatim lines, forbidden words. Load it in the generator (`json.load`) and pass the values into the setup/prepare code and `end_pair` instead of retyping them; write code from the `text` fallback where a field says `other`. If it has a `timeline`, a decision takes effect during the calls: key the code on `now` (both versions). Check edits with `python3 builder/spec_check.py out/<slot>.spec.json --api <api>`.
2. **Read the references.** `builder/FREYALIB.md` (the library, and its section "Policy as code" on `builder/policy.py`), `out/gen_brief-a_v3.py` (reference generator for a one-product brief) and `out/gen_brief-b_v3.py` (one to three products with notes), both on `builder/policy.py`. They encode ANOTHER bank's rules: take the structure, never the content. (`out/gen_brief-a_lib.py`, `out/gen_brief-b_lib.py` and `builder/MULTIPRODUCT.md` are the older prompt-decided payment flow.)
3. **Design the mapping.** For every rule decide where it lives, and write `# R12`-style comments next to the code:
   - **code node** for anything computable: business days, holidays, deadlines per band, floors, attempt proposals, callback windows, weekday words, counters (wrong answers, refusals, attempts). Do all arithmetic in code and hand the model finished facts as text (`{{facts}}`), including a day-by-day calendar with allowed/not allowed per product.
   - **tool definition** from the API: every body field as a leaf with the spec's type/description/enum; bake what the workflow knows (`customer_id`, `field`, `queue`, `outcome`), let the model fill the rest; descriptions say WHEN to call the tool.
   - **transition** for every state change: route on tool results (`ok_true`, counters, `wrong_answers_left`), on extracted enums (`who`, `topic`, `stance`, `confirm`) and on the `route` flag code writes, never on prompt text; deterministic conditions first. No model-judged exit in the payment part (`intent_tool('fin_refused')` is what `policy.py` replaces).
   - **hook** (`what_next_post`, `verify_post`, `promise_post`) so every tool result carries a `what_to_do_next` line in the brief's terms.
   - **prompt sentence** for conduct rules; verbatim sentences go into `on_enter` tts text or the terminal farewell, quoted exactly as the brief writes them.
4. **Write `out/gen_<slot>.py`** with `builder/freyalib.py` (`sys.path.insert(0, 'builder')`). Architecture rules:
   - The **initial node is a conversation node** (the opening). The chat route (used by the local simulator and the smoke tests) skips a first code node; simulations do not. Compute facts in code nodes entered after the first customer turn: `opening` (extract who answered) → `setup` (code, passthrough, routes on `who`) → `ask_<q1>` / `third_party` / `fin_*`. Every code node must be safe to run with partial state (`vars.get`, fallbacks).
   - One `ask_<field>` node per identity question, in the brief's order, `api_tool(api, "verify_identity", baked={"field": ...})`, `verify_post` with the API's hint values and the brief's wrong-answer limit. If the brief's limit is stricter than the service's, count wrong answers in a hook or code and route on your own counter.
   - **Speech normalisation**: every identity, promise and callback tool gets `pre=fl.normalise_pre({...})` on its spoken fields (`answer`, `amount`, `date`, `time`) with the brief's date order (`date_order='dmy'|'mdy'`; add `relative_days_code` + `relative_var` when the brief fixes how "next Friday" reads); identity prompts carry `fl.latest_value_note(N)`, and digit answers that are extracted use `fl.digit_extraction(name, N, desc)` (N from the brief/API).
   - **Four lessons from the hidden-path rehearsal (generated cases on Brief A, 14/19)**: when the brief says "first sentence", make the opening ONE sentence (two sentences cost the case); a human request at an identity question is NOT a refusal: give the refusal enum a `human` value routed back to the node with no counter (the prompt asks once whether you can help, then calls the transfer tool); "I don't know the exact day" after your question for the exact day is a vague offer (`offer_kind` vague), never `stance` refuse: say so in both descriptions; "ask once for another time" (third-party callbacks) and every other once-only ask is a counter in code (`fl.counter_code`), not a prompt sentence.
   - **Every spoken policy text comes from the brief**: `Policy(texts={...})` refuses to build without the brief's wording for `REQUIRED_TEXTS` (too much / floor line, paid, dispute, hardship, change after recording, human-first, no-talk, recorded, anything-else, vague, after-deadline, weekend-or-holiday, below-floor; plus the multi-product lines). Quote the brief's sentences; never leave a library default in.
   - **Never trust an extracted date for relative words**: the platform's date extraction uses the real clock, not the call's `now`. The policy nodes extract the customer's words (`offer_when`) and resolve them in code; pass the brief's rule for "next <weekday>" as `Policy(weekday_rule=...)`. Any other date a tool needs (callbacks) must come from code-built facts in the prompt, never from a `date`-type extraction.
   - **Side questions on policy turns**: give `Policy(asides={...})` every side question the brief answers (robot/AI, scam, who is calling, what is this about) with the brief's answer; the code prefixes it to the spoken line, because a turn routed through code into a tts line never reaches the dialogue model.
   - **A question back at an identity question is not a refusal**: give the refusal enum a `question` value (`fl.QUESTION_ENUM_CLAUSE`), route it to `fl.question_back_node(stage, ask_node, close_node)` (answer, ask again; the second question in a row with no answer counts as the brief's deflection) and put `pre=fl.reset_pre(["question_count_<stage>"])` on the identity tool. Measured: counting every question as a refusal closed 4 of 10 calls under the kit's asks_back style.
   - **Customers talk like people** (small talk, numbers and dates in two parts, self-corrections, questions back, words for numbers): `fl.assemble(..., conduct=True)` adds the library's conduct lines to the system prompt; append `fl.REFUSAL_NONE_CLAUSE` to every refusal/decline enum description (the brief's own list of what counts goes first) and `fl.PLAN_REQUEST_CLAUSE` to every plan-request enum description. Measured on the organisers' simulator: without these, small talk at a security question closed calls as declined and "how much can I pay instead?" became a transfer.
   - `get_account` in an `api_node`; a `prepare` code node computes per-product facts; the statement of the debt is a tts `on_enter` built in code from the brief's wording.
   - **The payment part is policy as code (`builder/policy.py`, the default architecture).** Every rule whose outcome can be computed from the call variables, tool results and extracted enums is decided in code or a route; a prompt only phrases what code decided. `POLICY = pol.Policy(holidays, texts={...the brief's sentences...}, multi=..., notes=..., note_reasons=..., fin_keys=...)`, then:
     - `prepare = POLICY.prepare_code(body, "statement")`: per product `register_product(vars, pid, words, full, floor, floor_name, deadline, rungs)` with the brief's band, floor, deadline and persuasion ladder (`rungs`, amount rules `full` / `floor` / `full_or_floor` = the floor once the customer said the full amount is too much), and the statement of the debt.
     - **negotiate → check_offer → confirm**: `POLICY.negotiate_node(task, [topic, stance, (offer_for,) offer_kind/date/amount], topic_transitions() + offer_guard_transitions() + stance_transitions())`. Every customer offer goes through the guard (weekend/holiday, after the deadline, below the floor, above the full amount, before today, vague), every agent offer is a code-built sentence from the ladder; enum descriptions quote the brief's own definitions (a proposed date or amount is never a refusal; 'too much' is not a plan request).
     - **Counters in code**: refusals per product (`attempts_used_<pid>`, exhausted → the refused ending or the product's note), the floor offered once, 'does not want to talk' twice, a human request asked once then transferred; hardship routes to `hardship_node`, where no offer is proposed (routing) but a named offer still goes through the guard.
     - **confirm**: `POLICY.confirm_node(...)`, read-back built in code (the brief's confirmation question), `change` → guard → read back again, never a transfer; `POLICY.record_nodes(nodes, api)` writes in an `api_request` node with the read-back values baked and asserted, retries as the brief says.
     - **Confirmed means a bank write, not a spoken claim**: a clear affirmative to the exact read-back routes directly and deterministically into the record node for the agreed products. Do not return to a dialogue node or say "scheduled"/"recorded" until the bank tool returns success. If the write fails, follow the brief's retry/error path. Exercise a plain "Yes, I confirm" against this route and inspect the ledger, not just the transcript.
     - **Wrap-up after a recorded promise**: `POLICY.wrapup_node(...)` speaks the recorded sentence and the brief's after-promise sentence, then gives the customer their next turn (nothing → promise ending; human → ask once, transfer; plan → restructuring; change → the brief's change sentence, promise unchanged; question → answer).
     - **`{{state_line}}` first** in every negotiation, confirm, hardship and wrap-up prompt (`POLICY.state_first`); `POLICY.add_event_nodes(nodes)` adds the policy code nodes. Unit-test the prepare and event code by exec with sample `vars` (see `builder/tests/test_policy.py`) before saving.
   - **Multi-product whenever the brief allows more than one product** (`Policy(multi=True)`): per-product band/deadline/floor/attempts, one question for all first, then one-by-one in the brief's order, one read-back for all, `add_note` per product without a promise when the brief uses notes (`notes=True`, reasons from the API's enum), the closing outcome by the brief's precedence (`fin_keys`; the `finalize` policy node). Build it even when the practice cases happen to have one product. If the brief's read-back or ordering rules differ from what `policy.py` does, implement the additional code in this run’s generator; never modify shared builder source during a run.
   - One `end_pair(key, outcome, reason, farewell)` per row of the brief's outcome/reason table, farewell with the brief's verbatim closing words; `close_call_tool(api, ...)` as the `end_of_call` lifecycle tool, enum from the API.
   - Say "recorded" only after `ok` true; retries exactly as the brief says; never end a turn without speaking or calling the next tool (put this in the system prompt).
   - **Cross-stage interrupts**: list every customer-facing conversation node, including third-party, wrong-number, callback retry, each identity question, negotiation, hardship, confirmation and wrap-up. For a human request, stop/quiet request, dispute or other globally applicable branch, check an explicit extraction and route in every relevant node. Use the brief's one-time help and transfer counters across stages, and never disclose account details to an unverified or third-party speaker. A path covered only in the main negotiation node does not implement a global rule.
   - **Never emit `test_variables`** (`assemble(..., test_variables=None)` or leave it out). On the chat route the tool bodies of conversation nodes take `customer_id` from `test_variables` instead of the call, so every bank call fails; without `test_variables` the real id is used (verified) and simulations are unaffected.
   - `assemble()` must pass; no `null`, no `{{` in code, booleans tested both spellings, every passthrough ends with `always`, every path reaches an end node.
5. **Generate and check locally.** `python3 out/gen_<slot>.py <api>`; `python3 builder/lint.py out/<slot>.workflow.json --api <api> --call-vars <the call variables the brief lists, e.g. customer_id,first_name,last_name,title,now> --rules out/<slot>.rules.json --budget` (fix every ERROR, read every WARN; without `--call-vars` a workflow shipped without test_variables gets one false warning per call-variable placeholder). Unit-test the date/amount code: execute the setup and prepare snippets locally with `vars` for two or three example products and the brief's `now`, print the facts, and compare with your own hand calculation from the brief (deadline per band, floor, attempt dates, callback window). Fix until they agree. `--rules` checks the workflow against the inventory (builder/LINT.md): every verbatim sentence must be fixed text, not a prompt line; the forbidden words before verification must not appear in pre-verification speech; a write tool reachable before verification gets a WARN to check against the brief; 'recorded'/'confirmed' must never be said before `ok: true`; `--budget` flags task_messages over 2500 characters (move facts into code-built text, deciding rules first).
   Inspect the route table for each globally applicable rule across the whole conversation, not just the happy path. Run a deterministic confirmation fixture that asserts a positive read-back reaches the bank write and only successful tool output permits the recorded line.
6. **Dry-run and save.** `python3 -c "import freya,json,sys; wf=json.load(open(sys.argv[2])); freya.validate_workflow(sys.argv[1], wf); print(json.dumps(freya.save_workflow(sys.argv[1], wf)))" <slot> out/<slot>.workflow.json` prints `workflow_id` and `agent_id`. The same slot updates the same workflow.
7. **Smoke.** Sequentially: `python3 builder/smoke.py <slot> --script builder/smoke_scripts/opening.json`, then `third_party.json`, then `wrong_number.json` (generic checks any collections brief must pass; adapt expectations only where this brief's wording differs). When a compatible practice customer is explicitly supplied, also run the talkative and asks-back persona scripts with its identity answers. They check that small talk and questions back do not count as refusal. Do not use the public bank's fixed customer identities or products for an unrelated hidden API. Fix failures in the generator.
8. **Audit.** `python3 builder/audit.py --rules out/<slot>.rules.json --workflow out/<slot>.workflow.json --generator out/gen_<slot>.py --out out/<slot>.audit.json`. Fix every active `partial`, `contradicted`, `missing` or unverified rule and the `top_fixes`; regenerate, lint, save. Audit again if time allows. For a rule that applies in several stages, verify every stage's route even if the audit marks it implemented; an excerpt in one node is not complete coverage.
9. **Practice cases, only when a cases file was given.** `python3 builder/sim.py <slot> --cases <file> --concurrency 3` (the chat route answers 504 above that) (local, parallel, needs OPENAI_API_KEY or falls back to the Claude CLI), or `python3 tools/run_cases.py <agent_id> --cases <file>` when the prompt says to use the organisers' simulation (one at a time, 3-11 minutes, run in the foreground and wait). Read every FAIL reason and the transcript; fix the generator (never the platform by hand); regenerate, save, rerun. At most three rounds. Stay inside the time budget given in the prompt.

   **No cases supplied (including hidden briefs).** The current runner does not create independent practice cases and the public mock bank supports only its fixed customers. Use lint, deterministic local branch fixtures derived from the given brief, API dry run, generic smoke calls, and a full rule audit. Never claim that these predict a hidden score. If a separate, schema-compatible diagnostic case file is explicitly supplied later, distinguish its generated expectations from official scoring and check any disputed failure against the brief before changing the agent.
10. **Finish** with one line: `workflow_id`, `agent_id`, number of nodes and tools, the last test result, and any rule you could not implement (say which and why).

## Rules

- Never edit the agent on the platform by hand. Change the generator and save.
- When a tool call fails, the agent must say so. It must never tell the customer something is recorded when it is not.
- A customer that passes once can fail the next time. Prefer rules in routes and code over rules in prompts.
- Keep tool definitions faithful to the API file: a field or enum value the brief mentions but the API lacks does not exist; one the API has but the brief does not mention still must be filled correctly.
- Time: the whole build must finish within the budget in the prompt. Save a working agent early (after step 6), then improve it.

## Submission runner constraints

The outer runner has strict final gates and owns submission export. Never change builder source, skills, input briefs, API files, case expectations or official test/scoring tools during a run. Resolve inventory errors by re-reading the brief and documenting the resolution in the generated code; do not weaken a check to turn it green. The generator may load this run’s spec; no value may come from a reference bank.

Use brief-sourced values explicitly for `Policy(fail_max=..., human_limit=..., notalk_limit=...)`, identity deflection counters, note and closing precedence. Disable silent amount/date capping in any older promise hook (`cap_to_deadline=False, cap_to_amount=False`). Validate proposed values before read-back; after a correction, clear agreement and read back the corrected values again before writing. Test boundary bands, floors, workweek/holiday dates and per-product write failures. For official practice runs, use the correct `--brief` filter and inspect three repetitions and people-like styles within the remaining budget. Diagnostic synthetic scores never establish official performance.

Multi-product consent: a date alone does not grant consent to every product. Extraction must identify the positively offered product, ignoring products mentioned in refusals. Use Policy.confirm_node so confirmation extracts fresh product scope; partial confirmation must reopen unconfirmed products and pass through their own policy attempts before any write. Never infer agreement to all products from a yes that explicitly names only one.

Before a long practice batch, audit first. Start with one repetition or a targeted subset, inspect failures and rerun corrections, then use three repetitions only when they fit. Run smoke scripts as separate commands. The runner reserves time for final platform export and audit, and can send unresolved findings back for up to two repair passes.

Counter scope and input presence must follow the brief. A per-call human-request limit uses the SAME `human_count` through identity, negotiation and wrap-up; do not reset it on verification. Identity questions and refusals that the brief counts as the same kind of deflection must feed one counter per applicable scope, with the prescribed first explanation. A genuine clarification question can be answered without a refusal only where the brief allows it. Validate each supplied callback component immediately, even if the other component is missing, and count invalid alternatives as prescribed. Use `Policy.offer_extraction` / `Policy.confirm_node` so an explicit zero or negative amount is distinguished from an absent amount (`offer_amount_present`); never infer a positive promise from zero. Call-wide stop-talking handling includes wrap-up, with outcomes following the brief’s precedence.
